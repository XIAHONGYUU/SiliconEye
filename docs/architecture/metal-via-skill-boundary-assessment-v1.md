# 金属／层间孔的skill边界评估 v1

2026-10-21。用户要求更新GitHub并评估skill拆分。本稿是架构建议和下一阶段验收设计，不表示金属／via专用skill或全幅重建工具已实现；当前材料入口仍以CURRENT_TASK为准。

## 建议：两个通用skill，各层分别配置与验收

按工作任务封装“金属重建”和“层间过孔重建”两个skill；不为M1、M2、M3分别复制skill，也不把金属与孔的判断揉成一个无法独立验收的步骤。共同的配准、证据、几何事务、复核页和质量门作为工具复用。

| 任务边界 | 建议skill | 每次调用的实例 | 主要输出 |
| --- | --- | --- | --- |
| 从照片恢复连续金属及真实间隙 | 金属重建 | 指定M1、M2、M3或其他已声明金属层 | 全幅规则几何、对象ID、来源与未知；不自动给出跨层网络 |
| 从照片恢复金属之间的孔及其落点 | 层间过孔重建 | 指定M1→M2的V1、M2→M3的V2等层对 | 孔／孔组几何、上下承载对象候选、来源、归属状态与未知 |

**skill是复用判断方法的边界；图层仍是独立数据、预算、状态和质量门的边界。** M1通过不能代表M2通过，V1通过不能代表V2通过；只修订指定图层和有依赖的局部，不把通用skill等同于每次重跑整栈。

## 共用什么，逐层保留什么

金属各层共用：原图观察→识别导体与分离→规则几何重建→邻层/接口核对→前后对照→范围化验收。宽线、折线、环、梳齿、板及dummy作为结构类型处理；判断方法可以选择不同算法，不能强制所有层采用同一阈值或算法。

层间孔共用：核实层对及证据帧→找有依据的孔/孔组→规则尺寸与阵列拟合→上下金属包围/对应→归属与隔离检查→交付。孔组足以支持接入时，不要求逐孔人工计数；精细几何质量与连接证据仍分别记录。

每层配置至少包含：层ID、邻层、来源照片及有效范围、原生/设计坐标与局部映射有效区、来源状态、规则配置引用、结构例外、已审对象和未决范围。每个数值规则记录单位、依据及适用范围；工艺/尺度未知不能填造物理最小尺寸。

每个孔层另外声明：`lower_layer`、`upper_layer`、`evidence_frames`、孔形/尺寸族、节距与上下包围预算。证据帧和连接层对分开：用户此前指出V1可在M1侧照片识别，不能硬编码“必须有独立V1照片”或“只能在M2图找V1”。单张去层照片也可能含金属和孔等多类信息。

2026-10-22的[联合小样裁决](../checkpoints/2026-10-22-m1-v1-m2-interface-reviewed.md)进一步提供反例：M1侧框内无V1，M2侧框内却有V2；原橙圈组的M1→V1→M2接入已确认。孔的层对身份和照片帧名必须分别保存，V2亮点不得当作V1拟合锚点。金属宽度、边缘无孔和阵列跨度可支持宏观结构对应，但“四排孔的距离”不等于四排V1，也不是精确像素批准；按这些描述自动补孔必须被拦截。

本轮接入前，`joint_layers`／`layer_review`接口只覆盖AA/POLY/CT；其后按下述统一注册表增量扩展了五层导体的只读复核，尚不支持任意M层／V层自动重建或修订。锁定快照、ID和复核机制继续复用，不能把M1记录塞进POLY字段、把V1当CT绕过层对检查。尚未实现的配置与能力仍按契约保留，不当作现成CLI参数。

2026-10-22的[M2／V2／M3小样](../checkpoints/2026-10-22-m2-v2-m3-joint-pilot.md)已在伴随模型工具中实现第二层对配置：共用几何／包围与原图面板，M2原记录冻结，V2身份接续，M3承载单独待审。V1默认门仍拒绝V2，不能靠换显示名绕过身份门；一个孔组支持区不输出为实测孔数。相对几何通过与跨层源图对应、人工接入确认分开，因此这只证明工具能表达第二层对，不证明全部金属／Via层已验证，也未扩展共同材料CLI或封装通用skill。

该小样随后获得[K1局部承载确认](../checkpoints/2026-10-22-m2-v2-m3-reviewed.md)：V2接入B1粗横向M3母线；精确投影及全幅／整网仍未验证。审批可增量接续并保持初版来源与几何，不再以“承载待审”阻塞本组接口，也不由此宣称通用skill已完成验收。

随后完成[连续五层中样及统一读取接口](conductive-layer-interface-v1.md)：导体注册表通过共同快照可选引用接入，`joint_layers`可加载／检查，`layer_review`可按层读取和显示。原AA／POLY／CT事务不改，导体编辑事务尚未扩展，不能将只读适配理解为所有层均可自动重建。两个已审层对已组装，后续仍需真实分支／隔离验证。

人审随后指出中样把M2的孔标作V1错误：本处为3×4 V2。当前按[来源身份纠错](../checkpoints/2026-10-22-m2-via-source-correction.md)保留M1侧V1、重建12个V2，并撤回原9对跨Via层配对及4.52像素留出的配准解释。通用skill必须在数值拟合前核实证据身份；拟合残差小和旧包回放一致都不能弥补孔层认错。

## 需要不同处理，但暂不需要另建skill的情况

- M1与CT端子对应密切，必须保留gate／源漏／环身份；更高层主要依赖相邻金属、孔及重复走线。
- 顶层宽金属、槽孔、pad、大板与细密信号线使用不同规则配置；不得为了同一模板把真实槽口填平。
- MIM／MOM电容区域需检查电极归属与介质隔离。不能因多层投影重叠便导通，也不能一概把电容附近的孔都排除；沿已确认的同电极接口重建。
- 颜色、反光、残留、明暗变化属于源图/观测策略差异，不应靠复制一个新skill来解决。

优先用通用方法＋按需读取的结构参考＋层配置解决差异。只有将来出现**不同目标、输入输出、质量门或操作权限**，且配置/结构模块不足以清楚表达，才单独拆skill。例如封装再布线或焊盘分析如果发展为独立任务，再据实评估，不现在预建占位skill。

## 和现有CT、追网流程的关系

CT保留独立skill：本项目CT关联AA/POLY与M1，已经包含沟道禁区、gate／源漏／环材料身份和人工裁决。金属间via的上下承载对象是明确层对中的金属，两者可共享方孔拟合、间距、包围、证据等底层工具；不把已审CT重命名或重新提取。

“指定一个端口，点亮整网”仍属于[金属网络追踪流程](../metal-tracing-workflow-v1.md)，应在金属／孔材料层之上消费对象和接口。它负责分支遍历、查完高层后回查所有下层接口、端点／照片边界和停止条件，不混入单层几何重建。已有v33是历史有范围连接证据，不能当作新M1几何或全部连接的自动批准。

不必等所有层一次完成才使用：可以先建立M1候选，再建立M2候选与V1观测，进行M1／V1／M2局部联合修订；随后迁移到M2／V2／M3。顺序按证据与依赖推进，不设“做完全部金属才能看孔”的硬流程，也不能只凭孔候选反向捏造两侧金属。

## 下一步最小验证范围

1. 选现有已审栅CT接入作M1锚点，保留gate／源漏／环区别；另覆盖转角/分支、窄间隙、dummy或电容邻域等不同结构。
2. 在共同全幅坐标建立M1规则几何小样，窗口只是评估视图，长线和未知延伸不在窗口边缘被裁断。原图对应与规则模型分开显示。
3. 扩展一个相邻M2窗口和V1接口，联合检查上下金属覆盖、真实接入、误并风险及源图对应；承载层或映射缺失时为待定，不当PASS或无孔。
4. 迁移到另一金属层及另一层对（如M3／V2），验证同一方法只换配置是否足够；没有第二类实例的证据时，只称已验证M1或V1路径，不宣称所有层验证完成。
5. 固定正反例：连续线被切断、近线误并、缺失分支、重复孔重叠/孔距不足、孔无上下承载、层对或来源帧误用、未经对齐的投影、MOM两极误并。软件测试验证规则能拦；AI试用另评首次判断、保留未知、漏检／误并与实际人工返工，不把自洽模型当照片真值。

人只裁决影响材料／连接身份的剩余歧义；已有批准和六处未知原样接续。完成跨层迁移与必要反例验证后再封装这两个skill；本次不提前创建SKILL.md、调度器或案例脚本。

## 官方规则回查与本项目推论

本次在线复核公开官方文档（main/latest，阅读日期2026-10-21），仅借鉴结构和配置分离，不认定本芯片工艺或移植尺寸：

- [GF180层定义§4.1](https://gf180mcu-pdk.readthedocs.io/en/latest/physical_verification/design_manual/drm_04_1.html)将Contact（Metal1到Active/Poly2）和Via1/Via2等相邻金属接口分列，也区分金属、dummy与slot。由此支持本项目明确层对、保持CT语义和金属结构例外；并不证明本照片的层号或工艺版本。
- [SKY130规则摘要，后端层表F3c/F3d](https://skywater-pdk.readthedocs.io/en/main/rules/summary.html)分别给出不同metal/via及工艺流的宽度、间距、包围信息。因此可以共用检查类型，不能共用一组无差别的数值预算。本文不将表中数值用于当前像素几何。
- [项目PDK识别参考](../reference/pdk-recognition-guide-v1.md)已有器件、电容与层关系入口；具体特殊结构按需回查，不因通用skill而取消来源检查。

“两个通用skill＋逐层配置与验收”是结合本项目目标和经验作出的架构建议，不是PDK文档对skill组织形式的规定。
